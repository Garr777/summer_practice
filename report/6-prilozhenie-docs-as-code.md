# Приложение А. Реализация Documentation-as-Code

Приложение документирует выполнение [задачи 5](1-vvedenie.md) практики. Отчёт
подготовлен по подходу Documentation-as-Code: его исходный текст является
артефактом репозитория, а итоговые документы формируются сборочным конвейером.

## А.1. Обоснование выбора инструментов

**Платформа: Gramax** [41] — открытая платформа документации как кода,
включённая в единый реестр российских программ для ЭВМ и баз данных. Выбор
обоснован тремя обстоятельствами:

1. **Хранение в Git в виде Markdown.** Каталог документации — это обычные
   файлы `.md` с заголовочным блоком YAML в репозитории, а не база данных.
   Следовательно, применимы все штатные средства работы с кодом: ветвление,
   история изменений, разрешение конфликтов, обзор изменений.
2. **Экспорт в DOCX по шаблону из командной строки.** Отчёт сдаётся в виде
   документа, оформленного по требованиям кафедры. Возможность применить
   корпоративный шаблон при экспорте переносит оформление из ручной операции в
   версионируемый артефакт.
3. **Соответствие контексту темы.** Применение отечественного открытого
   продукта согласуется с обоснованием актуальности
   ([раздел 2.2.1](2-problematika/2-aktualnost.md)) и даёт практическую проверку
   тезиса о работоспособности открытого стека.

**Разметка: Markdown** с заголовочным блоком. Выбран как формат, который читаем
без сборки, поддерживается визуальным редактором Gramax и допускает правку
любым текстовым редактором — в том числе научным руководителем, не работающим
с Git.

**Сборка: локальные скрипты-стадии.** Развёртывание отдельного сервера
непрерывной интеграции ради одного текстового документа не оправдано, поэтому
роль конвейера исполняют скрипты каталога `ci/`, воспроизводящие структуру
конвейера: границы стадий, немедленная остановка при отказе, каталог
артефактов. Конфигурация `.gitlab-ci.yml` **вызывает те же скрипты**, а не
дублирует логику, благодаря чему локальный и серверный прогоны не расходятся.

## А.2. Структура репозитория

```
summer_practice/
├── report/                    каталог Gramax — исходный текст отчёта
│   ├── .doc-root.yaml         параметры каталога
│   ├── _index.md              титульный лист и аннотация
│   ├── 1-vvedenie.md          … по одному файлу на раздел
│   └── …
├── ci/                        стадии конвейера, по скрипту на стадию
├── research/                  воспроизводимый поиск литературы
│   ├── search.py              набор запросов и их выполнение
│   ├── candidates.tsv         извлечённые записи
│   └── included.txt           отобранные источники
├── templates/                 шаблоны оформления DOCX и PDF
├── artifacts/                 результаты сборки (вне версионирования)
├── Makefile                   точка входа
├── .gitlab-ci.yml             зеркало ci/ для сервера
└── README.md                  инструкция по сборке
```

## А.3. Стадии конвейера

| Стадия | Назначение | Отказ означает |
|---|---|---|
| `lint` | структурные правила: наличие заголовочного блока, уникальность порядка разделов, отсутствие незавершённых фрагментов | документ соберётся, но будет оформлен неверно |
| `check` | штатная проверка каталога Gramax: внутренние ссылки, изображения, неподдерживаемые элементы | ссылка исчезнет из итогового документа |
| `sources` | требования к библиографии: объём, окно актуальности, согласованность ссылок и перечня | нарушено требование задания или ссылка указывает не на тот источник |
| `build:html` | сборка статического сайта | — |
| `export:docx` | формирование сдаваемого документа | — |
| `export:pdf` | формирование версии для чтения | — |

Две стадии заслуживают отдельного пояснения, поскольку они переводят
**требования задания** в автоматические проверки.

**Стадия `lint`.** Раздел без заголовочного блока выгружается в DOCX с именем
файла вместо заголовка, а два раздела с одинаковым значением порядка выходят в
произвольной последовательности. Обе ошибки невидимы в исходном Markdown и
обнаруживаются только при просмотре готового документа — то есть после того,
как он отправлен.

**Стадия `sources`.** Задание требует не менее 30 источников за последние 3–5
лет, каждый из которых процитирован в тексте. Стадия проверяет объём перечня,
долю источников внутри окна актуальности и **согласованность ссылок в обе
стороны**: ссылка на несуществующий номер приводит к отказу сборки, а
источник, ни разу не процитированный, — к предупреждению. Именно эта проверка
обнаруживает класс ошибок, возникающий при перенумерации перечня: ссылка
выглядит корректно и указывает не на ту работу.

## А.4. Воспроизводимость обзора литературы

Отдельное следствие подхода: воспроизводимым сделан не только документ, но и
**процедура его подготовки**. Каталог `research/` содержит набор поисковых
запросов и программу их выполнения, поэтому воронка отбора
([раздел 3.1.4](3-obzor-literatury/1-metodologiya-poiska.md)) не является
утверждением, которое следует принять на веру: она пересчитывается командой

```bash
python3 research/search.py
```

Содержательный отбор остаётся человеческим решением и зафиксирован в
`research/included.txt` — по одному идентификатору на источник, с отметкой о
способе его обнаружения. Это позволяет отличить источники, найденные основным
набором запросов, от полученных методом «снежного кома».

## А.5. Организация работы с Git

Ветвление соответствует структуре отчёта: основная ветка содержит проверенный
текст, а каждый раздел разрабатывается в ветке вида `docs/<раздел>` и
вливается после успешного прохождения конвейера. Такая организация даёт
историю, по которой видно, как собирался отчёт, и позволяет вести обсуждение
правок средствами обзора изменений.

Сообщения фиксаций описывают **содержательное изменение**, а не операцию с
файлами: не «правки в разделе 3», а указание на то, какое утверждение
добавлено или почему изменена формулировка.

## А.6. Оценка подхода

**Что подход дал.**

- Требования задания стали исполняемыми проверками, а не пунктами списка,
  которые нужно помнить при каждой правке. Согласованность 41 источника и
  ссылок на них в тексте проверяется за доли секунды.
- Оформление отделено от содержания: смена шаблона не затрагивает текст.
- История изменений позволяет ответить на вопрос «почему здесь написано именно
  так», обратившись к сообщению фиксации.
- Обзор литературы воспроизводим, что для научной работы имеет самостоятельную
  ценность.

**Чего подход стоил.**

- Начальная настройка инструментария заняла время, которое при работе в
  текстовом процессоре было бы потрачено на текст. Окупаемость наступает при
  многократном пересмотре документа и при наличии формальных требований,
  подлежащих проверке.
- Формулы в Markdown менее удобны, чем в специализированных средствах.
- Визуальный контроль вёрстки возможен только после сборки, поэтому
  расхождения оформления обнаруживаются с задержкой.

**Условия применимости.** Подход оправдан для документов, которые многократно
пересматриваются, имеют формализуемые требования и разрабатываются людьми,
уже работающими с системами контроля версий. Для однократно создаваемого
документа свободной формы издержки настройки не окупаются.
